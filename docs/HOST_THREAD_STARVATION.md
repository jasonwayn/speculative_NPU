# CMR 오버헤드는 알고리즘이 아니라 호스트 구현이었다

Date: 2026-08-21

## 결론

**호스트 쪽 세 가지를 고쳐 NPU 에서 CMR 이 처음으로 순이득이 됐습니다.**
16384 에서 stock 대비 **1.02(pg19) / 1.09(govreport) 배** — 기존 0.31 / 0.32 에서
**3.5~3.7 배** 올랐습니다. **그래프는 한 번도 안 건드렸고 tau 는 20/20 그대로입니다.**

| | 고친 것 | pg19 16384 |
|---|---|---|
| | (기존) | 7.99 tok/s |
| ① | `OMP_WAIT_POLICY=PASSIVE KMP_BLOCKTIME=0` | 20.00 |
| ② | `scores()` 의 GQA 물리 복사 제거 | 23.72 |
| ③ | `KST` 링버퍼 사전할당 | **29.31** (stock 28.62) |

①이 이 문서의 주제이고, ②③은 ①이 걷히자 드러난 호스트 병목입니다.

RBLN 런타임은 8 코어 머신에서 **OS 스레드를 32 개** 띄웁니다 (`/proc/self/status`).
거기에 torch 의 OMP 스레드가 병렬 구간이 끝난 뒤에도 busy-wait 으로 코어를 붙잡으면
**NPU 에 호출을 넣어줄 CPU 가 없어집니다.** NPU 가 느린 것이 아니라 호출이 스케줄링
대기에 걸립니다.

[LONG_CONTEXT_CMR.md](LONG_CONTEXT_CMR.md) 의 "NPU 는 tau 이득을 처리량으로 못 바꾼다"
는 결론은 **이 설정 문제였습니다.** 재측정본은 `results/corpus_passive/`.

## 1. 어떻게 찾았나

증상은 **타깃 그래프를 안 건드렸는데 verify 가 4 배 느려지는 것**이었습니다. CMR 을
켜면 `verify_ms` 가 17 → 91 로 갑니다. `tpre` 는 CMR 유무와 무관하게 라운드당 한 번,
16 칸 고정 shape 으로 호출되므로 타깃 연산 자체는 동일합니다.

4 인자 분해 ([bench/bench_sf_diag3.py](../bench/bench_sf_diag3.py), 4096 / pg19,
라운드당 ms, `results/verify_diag/`):

| | 구성 | draft | verify | append | score | tok/s |
|---|---|---|---|---|---|---|
| A | CMR 끔 | 6.5 | 22.0 | 8.6 | 0 | 43.6 |
| B | CMR 전체 | 10.1 | 90.5 | 39.1 | 34.1 | 9.8 |
| C | **스코어러만 제거** (Append 버스트 유지) | 6.5 | **17.1** | 24.5 | 0 | 33.0 |
| D | **Append 만 제거** (스코어러 유지) | 11.6 | **115.3** | 12.1 | 35.6 | 10.2 |

C 와 D 가 정반대 방향에서 같은 답을 냅니다 — **Append 는 무죄, 스코어러가 원인.**
H (`KST` 사전할당) 는 스코어러 자체 시간만 34 → 19 로 줄이고 verify 는 91.6 그대로라
**연산량 문제도 아닙니다.**

### 스레드 수 곡선이 역 U 자

| NTHREADS | 1 | 2 | 3 | 4 | 6 | 8 |
|---|---|---|---|---|---|---|
| verify ms | 18.1 | **86.7** | **81.2** | **81.5** | 55.7 | 18.7 |
| score ms | 10.9 | 32.1 | 26.1 | 26.3 | 16.3 | 5.9 |
| os threads | 33 | 34 | 35 | 36 | 38 | 40 |

**모든 실행 스크립트가 쓰던 `NTHREADS=2` 가 정확히 최악점이었습니다.** 스코어러 자체
시간도 같은 역 U 자라 순수 연산이 아니라 스레드 경합입니다. 왜 8 은 괜찮은지는
규명하지 못했습니다. `OMP_WAIT_POLICY=PASSIVE` 는 스레드 수와 무관하게 먹히므로
그것을 씁니다 (2 + PASSIVE 가 전 구성 최고).

`v_max` 가 180~230 ms 면 spin 이 켜진 것이고 PASSIVE 면 17~27 ms 로 떨어집니다.
진단 지표로 쓸 수 있습니다.

### 왜 오래 못 찾았나

**비용이 `score_ms` 가 아니라 뒤따르는 NPU 호출에 찍힙니다.** CMR 오버헤드
132 ms/round 중 34 ms 만 score 로 잡히고 **77 ms 가 verify/draft 로 샜습니다.**
타이머가 원인이 아니라 피해자를 가리키고 있었습니다.

[ROPE_ROOT_CAUSE.md](ROPE_ROOT_CAUSE.md) §4 의 "A 방식이 왜 전 구간을 느리게 만드는지
미규명" (verify 42 → 118 ms) 도 같은 종류일 가능성이 높습니다. 재확인 대상입니다.

## 3.5 ① 이후 드러난 두 병목

①로 스레드 경합이 걷히자 `score_ms` 안의 실제 연산이 보이기 시작했습니다.

### ② `scores()` 의 GQA 물리 복사

```python
Kr = K.repeat_interleave(s.rep, dim=1)   # [N,8,128] -> [N,32,128]
```

Qwen3-4B 는 KV 헤드 8, 쿼리 헤드 32 (GQA rep=4) 라 이 한 줄이 K 를 **4 배로 물리
복사**합니다. 16K 에서 67 → 268 MB 를 검색마다 새로 할당하고 씁니다.

격리 측정 ([checks/score_micro.py](../checks/score_micro.py), NTHREADS=2):

| N | 현행 | 배치 matmul | einsum 첨자 | 오차 |
|---|---|---|---|---|
| 1024 | 2.27 ms | 0.38 | 0.37 | 3.5e-10 |
| 4096 | 33.71 | 1.42 | 1.28 | 1.8e-10 |
| 8192 | 74.97 | 3.20 | 3.07 | 8.7e-11 |
| 16384 | **137.04** | **8.24** | 8.24 | 1.1e-10 |

**16.6 배**입니다. 오차 1e-10 은 fp32 결합순서 차이일 뿐입니다. einsum 자체는
322 MFLOP 뿐이고 **94% 가 그 268 MB 할당·복사**였습니다. 고친 코드:

```python
m = q.shape[0]
qg = q.view(m, s.nkv, s.rep, s.hd).permute(1, 2, 0, 3).reshape(s.nkv, s.rep * m, s.hd)
a = torch.matmul(qg, K.permute(1, 2, 0)) / math.sqrt(s.hd)   # [nkv, rep*m, N]
return torch.softmax(a, dim=-1).mean(dim=(0, 1))
```

### ③ `KST` 를 매 라운드 재할당

```python
KST = torch.cat([KST, scorer.keys(...)], dim=0)   # 라운드마다 저장소 전체 재할당
```

16K 에서 67 MB 입니다. ②를 고치자 이것이 `score_ms` 의 최대 항목이 됐습니다
(16384 에서 27.5 중 약 17). 링버퍼로 미리 잡고 제자리에 씁니다 — SpecExtend 도
`init_caches` 에서 같은 일을 합니다. `score_ms` 27.5 → **10.9**.

> ③은 ① 진단 때 한 번 기각했던 가설입니다. 그때 물었던 것은 "verify 부풀기를
> 고치는가" 였고 답은 아니오였습니다 (H: verify 91.6 유지). `score_ms` 자체는
> 그때도 34.1 → 19.0 으로 줄였습니다. **틀린 가설이 아니라 다른 질문이었습니다.**

청크 평균까지 접으면 `[1,512]` 로 더 줄어듭니다.

## 4.1 스코어링을 그래프로 옮기는 것은 **불가능합니다** (2026-08-21 조사 종료)

§4 의 제안을 실제로 시도했고 **벤더 제약에 막혔습니다.** 결론부터: **CMR 의 어텐션
점수는 호스트 CPU 에서 계산하는 것이 맞습니다.**

### 막힌 지점

`prefill_17` 과 `prefill_256` 은 `CompileContext(use_weight_sharing=True)` 로 가중치를
공유합니다. **한쪽 그래프에서 KV 캐시를 커스텀 어텐션 op 가 아닌 연산으로 읽으면
그 공유 맵이 깨져 다른 쪽 컴파일이 실패합니다** (순서 무관). 상세는
[VENDOR_LIMITS.md](VENDOR_LIMITS.md) §11.

우회로를 전부 시도했습니다.

| 시도 | 결과 |
|---|---|
| fused 커널의 softmax 읽기 | 불가 — 등록된 25 개 op 전부 `attn_output` 만 반환 |
| 옆에서 따로 계산 (격리 측정) | **1.12 ms** (호스트 10.9 ms), 오차 5.6e-08 |
| KV 캐시가 meta 텐서 | 해결 — `meta_tensor_names` 제거 (메모리 최적화일 뿐) |
| 5D 브로드캐스트 matmul | `IndexError: map::at` → 3D `bmm` 으로 해결 ([VENDOR_LIMITS.md](VENDOR_LIMITS.md) §12) |
| 청크 256 중간 텐서 671 MB | verify 그래프에만 점수 부착으로 해결 |
| **가중치 공유 맵 파손** | `use_weight_sharing=False` 로만 회피 |
| 공유 끔 + TP1 | 컴파일 OK, **로드에서 `SYS_ENOMEM`** (가중치 2 벌 16 GB > 15.7 GiB) |
| 공유 끔 + TP4 | **`DEVICE_GRAPH_CONVERSION` 컴파일 실패** |
| TP1 단일 그래프 (청크 17 만) | **동작함** — 컴파일·로드·실행 모두 OK |

마지막 구성만 살아남는데, 프롬프트 프리필을 17 토큰씩 964 회 돌아야 해서
프로덕션 구성이 아닙니다. **TP4 에는 경로가 없습니다.**

### 왜 접는 것이 맞는가

1. **TP4 에서 컴파일되지 않습니다** — 모든 성능 수치가 TP4 구성입니다
2. **이미 이기고 있습니다** — 16384 에서 stock 대비 1.02 / 1.09 배
3. **남은 이득이 결정적이지 않습니다** — 투영 1.26 / 1.36 으로 약 24 %p, 승패를 바꾸지 않습니다

### 그리고 "CPU 재계산" 자체는 비싸지 않았습니다

초기 66.4 ms 중 **실제 어텐션 재계산 몫은 10.9 ms 뿐**이었습니다.

```
원래                66.4 ms
OMP spin 끔         44.7      <- 스레드 경합 (구현)
GQA 물리복사 제거    27.5      <- 산술 낭비 (구현)
KST 사전할당        10.9      <- 메모리 재할당 (구현)
                    ────
                    10.9      <- 이것만이 "CPU 에서 다시 계산하는" 진짜 비용
```

55.5 ms 가 구현 낭비였고 전부 호스트에서 고쳤습니다. 그래서 NPU 로 옮길 유인이
처음 보였던 것보다 훨씬 작습니다. 라운드 61.6 ms 중 17.7% 이고, 길이별로는
1024 에서 3.9 ms, 16384 에서 10.9 ms (pg19) / 12.5 ms (govreport) 입니다.

재현 코드는 [compile/fused_score_1_256.py](../compile/fused_score_1_256.py) 에
남겨뒀습니다 (`SCORE_MODE` / `WSHARE` 로 각 시도를 재현할 수 있습니다).

## 5. 영향 범위

**이 저장소의 모든 NPU 수치가 `NTHREADS=2` + spin 상태에서 측정됐습니다.**

- 호스트 CPU 를 거의 안 쓰는 결과(5 종 벤치, RoPE 수정 전후, stock 코퍼스)는 약 **8~9%**
  과소평가 — 결론의 방향은 안 바뀝니다
- **CMR 관련 결과는 3.5~3.7 배 과소평가** — [LONG_CONTEXT_CMR.md](LONG_CONTEXT_CMR.md)
  §3 의 "3~7 배 손해" 와 "NPU 에서 CMR 은 순손해" 는 폐기하고 위 표로 대체합니다
- **에너지·전력 비교는 재측정하지 않았습니다.** 처리량이 3 배 올랐으므로 토큰당
  에너지도 크게 바뀝니다. [RESULTS.md](RESULTS.md) 의 GPU 대비 에너지 결론은
  현재 근거가 없습니다.

## 6. 어디에 반영돼 있나

세 수정 모두 프로덕션 코드에 들어갔습니다. 실행 스크립트에 env 를 안 넣어도 됩니다.

| | 위치 |
|---|---|
| ① | [bench/bench_sf_corpus.py](../bench/bench_sf_corpus.py) 상단 — `import torch` **보다 먼저** `os.environ.setdefault` |
| ② | [bench/bench_cmr_parts.py](../bench/bench_cmr_parts.py) `Scorer.scores` |
| ③ | [bench/bench_sf_corpus.py](../bench/bench_sf_corpus.py) `KSTB` 링버퍼 |

①은 **`import torch` 앞에 있어야** 합니다. OMP 런타임이 그 시점에 환경변수를 읽기
때문에 나중에 `os.environ` 을 바꿔도 효과가 없습니다.

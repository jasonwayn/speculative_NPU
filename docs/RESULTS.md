## 2. ⚠️ tau 교란 — tok/s 를 그대로 믿으면 안 되는 이유

**① → ② 는 tau·라운드 수·토큰 수가 완전히 같았습니다** (gsm8k 5.699 / 1131 / 6446,
math500 3.81 / 4356 / 16596). 생성 결과가 비트 단위로 동일했다는 뜻이고,
따라서 그 구간의 속도 향상은 순수한 하드웨어 이득입니다.

**③④ 에서는 tau 가 바뀌었습니다.**

| | tau | 라운드 수 | 토큰 수 |
|---|---|---|---|
| gsm8k ② → ③④ | 5.699 → 5.84 (+2.5%) | 1131 → 1113 | 6446 → 6500 |
| math500 ② → ③④ | 3.81 → 4.295 (**+12.7%**) | 4356 → 3398 | 16596 → 14595 |

tok/s 증가분을 분해하면:

```
gsm8k    라운드 -7.4%   +  tau +2.5%    =  +10.7%
math500  라운드 -12.5%  +  tau +12.7%   =  +28.8%
```

**하드웨어 이득은 라운드 시간(-7 ~ -12%) 쪽이고, math500 향상의 절반은 tau 입니다.**
tau 는 가중치·프롬프트·디코딩 수식이 정하는 값이라 하드웨어와 무관합니다.

원인 후보는 prefill 청크가 64 → 256 으로 바뀌면서 누적 순서가 달라져
프롬프트 hidden state 가 미세하게 달라지고, 첫 토큰이 갈리면 생성 궤적 전체가
달라지는 것입니다. [checks/tau_diag.py](../checks/tau_diag.py) 가 이걸 격리 검증합니다
(같은 프롬프트를 청크 64/256 으로 각각 prefill 해서 마지막 hidden state 의 cos 와
argmax 토큰을 비교).

**보고할 때는 라운드 시간을 쓰고, tok/s 는 이 단서와 함께 쓰세요.**

## 3. 오염된 측정 (쓰지 말 것)

`paper_results/humaneval.txt`, `paper_results/mbpp.txt` 는 **다른 카드에서 A/B 실험을
병행하는 동안 측정**됐습니다. verify 가 63.9 → 225.2 / 245.2 ms 로 튀었습니다.

카드는 독립이지만 호스트가 공유 자원입니다 — 워커당 19.5 GiB RSS 대 64 GiB 상한,
8 코어, 모델 로딩이 flock 으로 직렬화. **측정은 카드 1장 단독으로 해야 합니다.**

`mt-bench` 는 오염되지 않았지만 tau 2.303 으로 다른 데이터셋과 성격이 많이 다릅니다
(멀티턴 대화).

## 5. 실패로 확인된 방향

| 시도 | 결과 |
|---|---|
| flash attention (`-16k-flash`) | 5–15% 악화. partition 8192 가 우리 컨텍스트(4K)보다 큼 |
| 청크 32 / 16 / 8 | 악화. 호출당 바닥 비용 약 37 ms = 8.04 GB ÷ 225 GB/s |
| verify 청크 128 / 256 | 악화 (16토큰 검증: chunk17 39.5 ms vs chunk256 112.9 ms) |
| `.float()` 제거 | 차이 없음. 단독 A/B 65.95 vs 62.98 tok/s (노이즈 약 10%) |
| int4 / int8 | 출력 붕괴 (토큰 id 0 무한 반복) |
| `decoder_batch_sizes` 다중 배치 | 컴파일은 되나 작은 배치 실행 불가 |

## 6. 비용 모델

```
prefill 호출 비용 ≈ 37 ms  +  positions × 0.09 ms
                    └ 가중치 스트리밍 8.04 GB ÷ 225 GB/s (위치 수 무관)
```

**청크 안에서의 패딩은 거의 공짜이고, 청크 경계를 넘는 순간 비용이 두 배가 됩니다.**
그래서 "패딩 위치 수"로 낭비를 세면 크게 과대평가하게 됩니다.

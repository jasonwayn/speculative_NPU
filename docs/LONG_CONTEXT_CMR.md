# 긴 컨텍스트에서의 tau 붕괴와 CMR — NPU 재현

Date: 2026-08-21

## 요약

**GPU 에서 관찰된 CMR 의 긴 컨텍스트 이득이 NPU 에서 그대로 재현됩니다.**
tau 는 두 하드웨어에서 2~3% 안으로 일치합니다. **다만 NPU 에서는 CMR 의 오버헤드가
tau 이득을 압도해 처리량이 3~7배 떨어집니다.** 같은 알고리즘의 손익 부호가
하드웨어에 따라 뒤집힙니다.

---

## 1. 실험 조건

| | |
|---|---|
| 입력 | **실제 문서** — pg19(책), govreport(미국 GAO 보고서) |
| 길이 | 1024 / 2048 / 4096 / 8192 / 16384 (실측 995 ~ 16355 토큰) |
| 지시문 | `Summarize the following document.` |
| 샘플 | 길이당 5개 |
| 생성 | `max_new_tokens=256`, greedy |
| CMR | budget 1024, chunk 32, top-k 32, every 4 steps |
| NPU | ATOM+ 4장 (TP4), RoPE 수정판, `max_seq_len=20480` |

입력은 GPU 하네스(`spec/cmr/run_cmr.py`)의 `build_inputs_corpus` 를 그대로 옮겨
토큰 id 로 덤프한 뒤 NPU 로 전송했습니다 — **양쪽이 같은 문서·같은 토큰**을 봅니다.

> ⚠️ 샘플은 토큰 스트림에서 정확히 N개를 잘라내므로 문장·문단 경계를 무시합니다.
> pg19 는 책 한 권이 50K+ 토큰이라 16384 도 한 권 안에서 연속이지만,
> **govreport 는 평균 9.4K 라 16384 에서 여러 보고서가 이어집니다.**
> 16K 결과는 pg19 를 주 근거로 읽으세요.

무너졌을 것입니다 (`results/sf_results/` 의 `len16000_cmr0` = 1.097).

## 3. 처리량 — NPU 에서는 CMR 이 순손해

| 길이 | pg19 stock | pg19 CMR | govreport stock | govreport CMR |
|---|---|---|---|---|
| 1024 | 73.1 tok/s | 10.6 | 88.4 | 12.0 |
| 4096 | 63.7 | 9.8 | 64.6 | 10.2 |
| 8192 | 40.7 | 8.3 | 45.5 | 9.7 |
| 16384 | 26.2 | 8.0 | 29.8 | 9.6 |

**tau 가 28~37% 오르는 16384 에서도 처리량은 3.1~3.3배 떨어집니다.** 짧은 길이에서는
7배까지 벌어집니다.

원인은 CMR 의 두 비용입니다.

**① 호스트 스코어링.** `Scorer` 가 타깃 레이어 35 의 어텐션을 CPU 에서 재계산합니다
(`32헤드 × 쿼리 × 전체키` softmax). 컨텍스트 길이에 선형으로 늘어납니다.
4096 에서 라운드당 39.4 ms 였습니다.

**② 압축본 재기록.** 검색마다 선택된 약 1008개 위치를 드래프터 캐시에 **0번부터 다시
씁니다.** Append 그래프 폭이 16 이라 검색 한 번에 약 63회 호출입니다.
4096 측정: `append_ms 4.1 → 32.6`, `verify_ms 13.0 → 92.3`.

GPU 에서는 두 비용이 훨씬 싸므로(동적 shape, 커널 한 번) 순이득이 났습니다.

## 4. CMR 구현 메모

**드래프터 캐시만 자릅니다.** 타깃의 `VL` 과 `cache_position` 은 건드리지 않습니다.
타깃을 자르면 투기 디코딩이 무손실이 아니게 되기 때문입니다 — 드래프터를 자르면
tau 만 떨어지고 정확도는 그대로입니다.

**메모리는 안 줄어듭니다.** 캐시 텐서는 `MAXC` 로 정적 할당돼 있고 CMR 은 읽는 길이
(`ctx_len`)만 줄입니다. NPU 에서는 연산량만 아낍니다.

**선택 규칙** (`bench_cmr_parts.pick_chunks`)

```python
means = 청크(32칸)별 평균 어텐션 확률
keep  = topk(means, 32)     # 점수 상위 32청크
keep.add(n - 1)             # 최신 청크 강제
idx   = [keep 의 위치들, 오름차순]
return idx[:budget]         # 1024 로 절단
```

점수는 **로짓이 아니라 softmax 확률**이고, 타깃 레이어 35 의 32개 헤드와 최근 쿼리
M개의 평균입니다. 즉 "타깃이 지금 어디를 보고 있는가"입니다.

> `idx[:budget]` 이 **위치 오름차순 앞에서부터** 자르므로, 초과가 나면 방금 강제로
> 넣은 최신 청크가 잘립니다. 이번 실험에서는 `kept_mean` 이 전 구간 1008 로
> 예산(1024) 아래여서 발생하지 않았습니다. 설정을 바꾸면 걸릴 수 있습니다.

## 5. 남은 질문

**CMR 의 tau 이득은 진짜인데 NPU 구현이 그걸 못 살립니다.** 오버헤드를 어디까지
줄일 수 있는지가 문제입니다.

- 스코어링을 NPU 로 이관 — 단, 그 경로도 RoPE 를 쓰므로 범위 축소 수정이 필요합니다
  (`Scorer._rope` 가 `e.cos()`/`e.sin()` 을 그대로 부릅니다. 지금은 호스트라 무해)
- 재기록 비용 축소 — Append 폭 16 → 256 이면 검색당 63회 → 4회
- 검색 주기(`every-n-steps 4`) 조정

이것들을 적용했을 때 손익분기가 8192 아래로 내려오는지가 다음 실험입니다.

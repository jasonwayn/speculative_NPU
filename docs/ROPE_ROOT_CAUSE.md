# 긴 컨텍스트 tau 붕괴의 원인 — RBLN 삼각함수 정확도

Date: 2026-08-20

이 문서가 [LONG_CONTEXT_ROOT_CAUSE.md](LONG_CONTEXT_ROOT_CAUSE.md) 를 대체합니다.
그 문서의 결론(K=1041 shape 의존 결함)은 **재현되지 않았습니다.** 아래 1절 참고.

---

## 결론

**RBLN 의 `sin`/`cos` 는 인자가 커질수록 무너집니다.** 절대오차가 `약 6e-4 × |x|` 로
인자에 비례합니다. Qwen3 는 `rope_theta = 1e6` 이라 최고주파 차원의 `inv_freq` 가 1 —
**RoPE 각도(라디안)가 곧 position 값**이 되어 정면으로 걸립니다.

드래프터만 걸린 이유는 optimum-rbln 이 타깃의 `rotary_emb` 를 **traced 영역 밖에서**
만들어 넘기기 때문입니다 (`prepare_forward_args` 가 반환). 드래프터는 stock HF 구현을
그대로 트레이스해서 NPU 가 직접 sin/cos 를 계산하고 있었습니다.

**수정**: 호스트에서 `pos × inv_freq` 의 **2π 나머지**만 구해 넘기고, sin/cos 계산은
그래프에 남깁니다. 코드는 [bench/draft_two_rr.py](../bench/draft_two_rr.py).

---

## 1. 앞선 진단이 재현되지 않은 부분

`LONG_CONTEXT_ROOT_CAUSE.md` 는 "청크 17/1024 컨텍스트에서 K=1040 은 정상(cos 0.999972,
16/16), K=1041 은 붕괴(cos 0.853079, 5/16)" 를 결정적 근거로 제시했습니다.
[checks/pad_discriminator.py](../checks/pad_discriminator.py) 로 같은 설정을 재현한 결과:

| | 문서 주장 | 실측 |
|---|---|---|
| K=1040 NPU vs CPU | 0.999972 | **0.852810** |
| K=1041 NPU vs CPU | 0.853079 | 0.853079 |
| NPU(1040) vs NPU(1041) | — | **0.999972** |

**1040 도 똑같이 틀립니다.** 문서의 두 숫자는 실측에서 그대로 나오지만 `0.999972` 는
NPU-vs-CPU 가 아니라 **NPU-vs-NPU** 값입니다. shape cliff 는 존재하지 않습니다.

마스크 배제 논리도 무효였습니다. 마스크 값을 `-100 / -1e4 / -1e9 / finfo.min` 으로 바꿔도
결과가 같다는 근거였는데, **네 값 모두 `exp()` 후 0 이라 마스크가 적용되든 무시되든
결과가 같습니다.** 판별력이 없습니다. 제대로 된 판별은 마스크 값이 아니라 **마스킹된
자리의 내용**을 바꾸는 것이고, 큰 난수를 넣어도 출력이 비트 단위로 안 변했습니다
(cos 1.000000) — 마스크는 정상입니다.

## 2. 진짜 원인 — 길이가 아니라 position 값

"컨텍스트 길이 곡선" 은 교란된 관측이었습니다. 길이가 늘면 블록의 position 값도 같이
커지기 때문입니다. **K 를 272 로 고정하고 position 만 옮기면** 바로 드러납니다
([checks/pos_vs_len.py](../checks/pos_vs_len.py)):

| position | cos_min |
|---|---|
| 0..272 | 0.99791 |
| 384..656 | 0.98840 |
| 768..1040 | 0.83612 |
| 3000..3272 | 0.76034 |
| (대조) K=1040, pos 0..1040 | 0.85281 |

같은 데이터, 같은 K, position 만 다른데 무너집니다.

## 3. 삼각함수 단독 측정

모델도 가중치도 없이 그래프가 `torch.sin(x), torch.cos(x)` 두 줄인 스크립트로 재현됩니다
([checks/sincos_probe.py](../checks/sincos_probe.py), [checks/cpu_vs_npu_trig.py](../checks/cpu_vs_npu_trig.py)).

### 같은 서버, 같은 입력, 기준은 CPU float64

| 입력 범위 | **NPU fp32** | **CPU fp32** | CPU fp16 | NPU/CPU |
|---|---|---|---|---|
| [0, 2π) | 6.2e-03 | 3.5e-08 | 2.0e-03 | 1.8e5 |
| [0, 100) | 6.2e-02 | 3.6e-08 | 3.1e-02 | 1.8e6 |
| [0, 1000) | 4.9e-01 | 3.5e-08 | 2.5e-01 | 1.4e7 |
| [0, 4096) | 1.67 | 3.6e-08 | 9.6e-01 | 4.7e7 |
| [0, 1e5) | 2.00 | 3.5e-08 | nan | 5.8e7 |
| [0, 1e8) | 2.00 | 3.3e-08 | nan | 6.0e7 |

sin/cos 값역이 [-1,1] 이므로 **오차 2.0 은 참값과 완전히 무관하다는 뜻**입니다.

- **CPU fp32 는 1e8 까지 완전히 평평합니다** (3.3e-08, fp32 ulp 한계). 하드웨어 한계가
  아니라 구현 문제라는 뜻입니다.
- **NPU 는 fp32 자리를 쓰면서 fp16 보다 나쁩니다** — [0,2π) 에서 6.2e-3 vs fp16 2.0e-3.
- fp16 은 65504 를 넘으면 `nan` 을 냅니다. NPU 는 **조용히 2.0 을 냅니다.** 더 위험합니다.

### 범위 축소 문제인지 확인

`1.2346 + k × 2π` 는 k 와 무관하게 참값이 같습니다. 그런데:

| x | sin 오차 | cos 오차 |
|---|---|---|
| 1.2346 + 0×2π | 3.3e-04 | 1.5e-04 |
| 1.2346 + 10×2π | 1.8e-02 | 5.6e-02 |
| 1.2346 + 1000×2π | 1.94 | 2.3e-01 |

**답은 같은데 인자만 커지면 틀립니다.**

### fp16 절단 가설은 기각

오차 크기가 fp16 ulp 와 자릿수까지 맞아서 "인자를 fp16 으로 자른다" 를 의심했지만,
**이미 fp16 격자 위에 있는 값만 넣어도 오차가 그대로**입니다
([checks/fp16_hypo.py](../checks/fp16_hypo.py)). 입력 절단이 아닙니다.

결국 하나의 법칙입니다: **절대오차 ≈ 6e-4 × |x|** (상대정밀도 약 11비트).
"작은 값에서는 잘한다" 가 별개 능력이 아니라, 같은 상대오차가 작은 수에 곱해질 뿐입니다.

## 4. 수정

두 가지를 시도했고 **B 를 채택**했습니다.

| | 방식 | 정확도 | 속도 |
|---|---|---|---|
| A | cos/sin 을 호스트에서 계산해 그래프 입력 2개 추가 | 16/16 | **전 구간 2~15배 악화** |
| **B** | **호스트는 2π 나머지만, sin/cos 는 그래프가 계산** | **16/16** | **기존과 동일** |

A 는 `pos [1,16] int32` 외에 `cos`/`sin [1,16,128] fp32` 를 **추가**합니다. 그러면
draft 5.7→19.1, verify 42.2→118.5, append 1.9→31.2 ms 로 벤치 전 구간이 느려집니다.
**타깃 그래프는 건드리지도 않았는데 verify 까지 느려집니다.** 메커니즘은 규명하지
못했습니다. 격리 측정에서는 재현이 불안정했고, 벤치에서는 2회 반복 모두 재현됐습니다.

B 는 `pos [1,16] int32` 를 `angle [1,16,64] fp32` 로 **대체**합니다 — 입력 개수가
안 늘어납니다. 이것만으로 A 의 부작용이 완전히 사라집니다.

```python
# 호스트 (fp64)
def host_angle(pos, inv, dtype):
    f = pos.double().unsqueeze(-1) * inv.double().view(1, 1, -1)
    return torch.remainder(f, 2 * math.pi).to(dtype)

# 그래프 — 인자가 항상 [0, 2π) 안
def _cs(angle):
    e = torch.cat([angle, angle], dim=-1)
    return e.cos(), e.sin()
```

범위 축소 후에도 NPU 오차는 5e-3 남습니다 (fp32 면 1e-7). 하지만 **position 과 무관하게
평평**해서 실용상 문제가 없습니다.

## 6. 아직 안 한 것

- **20샘플 5종 재측정.** [RESULTS.md](RESULTS.md) 의 `slim_results` 표와 GPU 비교는
  전부 **수정 전** 수치입니다. 특히 math500 의 tau 4.295 는 이 결함 때문일 가능성이
  높습니다 (수정 후 5샘플 기준 7.293 으로 GPU 6.661 을 넘음).
- 프로덕션 `draft_two.py` 와 `fused_*` 그래프는 **안 건드렸습니다.** 수정은 별도 파일
  (`draft_two_rr.py`, `bench_sf_rr.py`) 에 있습니다.
- A 방식이 왜 전 구간을 느리게 만드는지 미규명.

## 7. 벤더에 보낼 최소 재현

`checks/sincos_probe.py`, `checks/cpu_vs_npu_trig.py` 는 가중치도 데이터셋도 필요 없고
그래프가 `torch.sin(x), torch.cos(x)` 가 전부입니다.

> RBLN-CA22 / rebel-compiler 0.10.2. `torch.sin(x)`, `torch.cos(x)`, 입력 `[1,4096] float32`.
> 절대오차가 `약 6e-4 × |x|` 로 인자에 비례해 증가, |x|≈4096 에서 1.67 (값역 [-1,1]).
> 같은 머신 CPU fp32 는 |x|=1e8 까지 3.3e-08 로 평평 — **최대 6천만 배 차이**.
> fp16 으로 계산한 것보다도 나쁨. `x` 와 `x+1000·2π` 는 참값이 같은데 오차가
> 3.3e-04 → 1.94. 인자를 fp16 격자에 미리 맞춰 넣어도 동일하므로 입력 절단은 아님.
> 범위를 넘어가면 `nan` 이 아니라 **조용히 무관한 값**을 반환.
